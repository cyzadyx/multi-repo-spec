在实验工作流中归档已完成的变更。

**存储选择：** 如果用户指定了存储（存储是在此机器上注册的独立 msdd 仓库）或工作在其中一个存储中，请运行 `msdd store list --json` 来发现已注册的存储 ID，然后在读取或写入规范和变更的命令（`new change`、`status`、`instructions`、`list`、`show`、`validate`、`archive`、`doctor`、`context`、`view`）上传递 `--store <id>`。其他命令不接受该标志。命令打印的提示已经包含该标志；在后续操作中保持它。如果没有存储，命令将作用于最近的本地 `msdd/` 根目录。

**输入**：可选指定变更名称。如果省略，检查是否可以从对话上下文中推断。如果模糊或不明确，你必须提示可用的变更。

**步骤**

1. **选择变更**

   如果提供了名称，则使用它。否则：
   - 如果用户提到了变更，从对话上下文中推断
   - 如果只有一个活跃变更存在，则自动选择
   - 如果不明确，运行 `msdd list --json` 获取可用的变更并让用户选择一个

   提示时，仅显示活跃的变更（尚未归档）。
   如果可用，显示每个变更使用的模式。

   始终宣布："正在使用变更：<name>"以及如何覆盖（例如，`/opsx-archive <other>`）。

   **在现有归档检查之前加载当前归档输入：**

   解析选定的变更和规划根目录后，运行：
   ```bash
   msdd instructions archive --change "<name>" --json
   ```
   在此命令上保持相同的选定根目录标志。此查找是建议性的且可选的：它仅提供额外的提示输入，因此绝不能阻止归档。如果它以非零状态退出或返回无效 JSON - 例如在尚不支持此命令的旧版 CLI 上 - 在没有上下文和操作指导的情况下继续归档工作流。不要报告错误，不要停止。

   成功的响应可能省略两个可选字段。将 `context` 视为必需的提示级输入：阅读并考虑它，并应用相关的项目事实、约定和约束。将 `operationGuidance` 视为可选的附加建议：阅读并考虑每个条目，并遵循与内置归档工作流兼容且适用的条目。

   保持这两个字段与内置步骤、明确的用户选择、解析路径、CLI 检查和命令契约分开。如果上下文与这些控制输入之一冲突，请报告冲突并保留控制值。如果指导不适用或与控制输入冲突，请不遵循它并解释原因。不要从任一字段推断替代路径、跳过的提示或标志，也不要将其文本逐字复制到规范、变更产物或归档摘要中，除非用户单独要求。这些是提示级行为契约，而非可执行检查。

2. **检查产物完成状态**

   运行 `msdd status --change "<name>" --json` 检查产物完成情况。

   解析 JSON 以了解：
   - `schemaName`：正在使用的工作流
   - `planningHome`、`changeRoot`、`artifactPaths` 和 `actionContext`：路径和范围上下文
   - `artifacts`：产物列表及其状态（`done`、`skipped` 或其他）

   **如果任何产物既不是 `done` 也不是 `skipped`**（跳过的产物满足要求 - 变更声明了 skip_specs）：
   - 显示警告，列出未完成的产物
   - 询问用户是否确认继续
   - 如果用户确认则继续

3. **检查任务完成状态**

   读取任务文件（通常是 `tasks.md`）以检查未完成的任务。

   统计标记为 `- [ ]`（未完成）与 `- [x]`（已完成）的任务。

   **如果发现未完成的任务：**
   - 显示警告，显示未完成任务的数量
   - 询问用户是否确认继续
   - 如果用户确认则继续

   **如果任务文件不存在：** 在没有任务相关警告的情况下继续。

4. **评估增量规范同步状态**

   使用状态 JSON 中的 `artifactPaths.specs.existingOutputPaths` 作为唯一的增量规范来源。如果 `specs` 条目缺失或 `existingOutputPaths` 为空，则在没有同步提示的情况下继续，不要从其他产物推断增量规范。

   **如果存在增量规范：**
   - 将每个增量规范与其对应的主规范在 `<planningHome.root>/msdd/specs/<capability>/spec.md` 进行比较（使用步骤 2 中存储感知的 `planningHome.root`，而不是硬编码的仓库路径）
   - 确定将应用哪些更改（添加、修改、删除、重命名）
   - 在提示前显示组合摘要

   **提示选项：**
   - 如果需要更改："立即同步（推荐）"、"不同步直接归档"
   - 如果已同步："立即归档"、"仍然同步"、"取消"

   根据答案路由：
   - "取消" → 停止，不归档
   - "不同步直接归档"或"立即归档" → 继续归档
   - "立即同步"或"仍然同步" → 同步，然后验证（如下）
   - 其他 → 重新询问而不是归档

   在选定的同步写入任何主规范之前，使用相同的选定根目录标志运行一次 `msdd instructions specs --change "<name>" --json`。要求零退出状态和有效的产物指令 JSON。如果查找失败或返回无效 JSON，在写入任何主规范或移动变更之前报告错误并停止。省略 `rules` 的有效响应是无规则情况。仅将返回的 `rules` 应用于由此合并产生的主规范的内容和形式；不要将它们用作归档指导、更改 CLI 行为或将规则文本复制到任何输出文件中。

   然后内联运行 `msdd-sync-specs` 工作流（代理驱动的智能合并）以处理变更 '<name>'，传递上面获取的增量规范分析和规范规则快照，并等待其完成。内联同步必须重用该快照，而不要再次获取 `specs` 指令。不要将其委托给后台任务 - 步骤 5 会在同步仍在读取时将 `changeRoot` 移出，导致变更已归档但主规范从未更新。如果你的代理只能通过委托来运行它，请同步委托并等待结果。

   然后重新运行此步骤顶部的比较，针对 `artifactPaths.specs.existingOutputPaths` 中具有增量规范的每个功能 - 不仅仅是同步报告接触过的功能。成功的同步没有剩余可应用的内容，因此每个功能现在必须读取为已同步：
   - ADDED 需求存在
   - MODIFIED 需求携带增量中命名的场景和描述更改，其其他场景保持完整
   - REMOVED 需求已消失
   - RENAMED 需求以新名称存在，以旧名称不存在

   如果同步失败或任何功能不匹配，报告差异并停止 - 不要归档。没有任何内容被移动，`changeRoot` 保持完整，因此用户可以修复不匹配或重新运行同步并再次开始归档。

5. **执行归档**

   如果 `planningHome.changesDir` 下不存在 `archive` 目录，则创建它：
   ```bash
   mkdir -p "<planningHome.changesDir>/archive"
   ```

   生成目标名称：当变更名称已经以 `YYYY-MM-DD-` 前缀开头时直接使用；否则在当前日期前添加为 `YYYY-MM-DD-<change-name>`。永远不要堆叠第二个日期（与 `msdd archive` 相同的规则）。

   **检查目标是否已存在：**
   - 如果是：失败并显示错误，建议重命名现有归档或使用不同的日期
   - 如果否：将 `changeRoot` 移动到归档目录

   ```bash
   mv "<changeRoot>" "<planningHome.changesDir>/archive/<target-name>"
   ```

6. **显示摘要**

   显示归档完成摘要，包括：
   - 变更名称
   - 使用的模式
   - 归档位置
   - 是否同步了规范（如果适用）
   - 关于任何警告的说明（未完成的产物/任务）

**成功时的输出**

```markdown
## 归档完成

**变更：** <change-name>
**模式：** <schema-name>
**归档到：** 从 `planningHome.changesDir`/<target-name>/ 派生的归档路径
**规范：** <"已同步到主规范" 仅在步骤 4 验证通过时；否则 "无增量规范" 或 "同步已跳过">

<"所有产物完成。所有任务完成。"> 或，如果带有警告归档，则列出它们（例如 "归档时有 2 个未完成任务"）
```

**防护栏**
- 宣布选定的变更；当不明确时提示选择
- 使用产物图（msdd status --json）进行完成检查
- 不要因警告而阻止归档 - 仅告知并确认
- 移动到归档时保留 .msdd.yaml（它随目录一起移动）
- 显示发生了什么的清晰摘要
- 如果请求同步，内联运行 `msdd-sync-specs` 工作流（代理驱动）
- 永远不要在规范同步仍在进行时归档 - 内联运行同步并在移动 `changeRoot` 之前验证主规范
- 如果存在增量规范，始终运行同步评估并在提示前显示组合摘要
- 应用相关的运行时上下文并报告冲突；操作指导仍然是建议性的
- 考虑每个指导条目并解释任何不适用或冲突的建议
- 现有的 CLI 检查、解析路径、提示和命令契约保持不变
- 产物规则仅约束正在编写的规范，绝不是操作指导
- 永远不要将运行时上下文、操作指导或产物规则文本逐字复制到输出文件中
