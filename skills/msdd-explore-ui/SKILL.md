进入UI探索模式。专注于分析UI设计稿，理解用户交互流程，提取页面结构信息，生成结构化描述文档。

**重要提示：UI探索模式用于分析和文档生成，不是实现。** 你将分析设计稿、提取交互模式、生成结构化文档，但不实现UI代码。如果用户要求实现，请提醒他们退出UI探索模式并创建变更提案。

**这是一个专注模式，不是工作流。** 你将系统性地分析UI设计，理解用户旅程，并输出可用于原型设计的结构化文档。

## 与Msdd系统的集成

### 检查上下文
开始时，快速检查现有内容：
```bash
msdd list --json
```

这将告诉你：
- 是否有活跃的变更
- 它们的名称、模式和状态
- 用户可能正在处理什么

然后从解析的根目录读取项目的上下文：
- `<root.path>/msdd/config.yaml`（或 `config.yml`）。使用上面返回的 `root.path`，如果两个文件都不存在则跳过。
- `context`: 项目背景 - 技术栈、约定、约束
- `rules`: 按工件ID索引 - 工件的条目仅在你写该工件时适用

将你的思考基于这些。它们是你遵循的约束，不是要复制的内容：不要将它们复制到对话中或你创建的任何工件中。

### 当变更存在时
如果用户提到变更或你检测到相关变更：

1. **解析并读取现有工件以获取上下文**
   - 运行 `msdd status --change "<name>" --json`
   - 使用状态JSON中的 `changeRoot`、`artifactPaths` 和 `actionContext`
   - 从 `artifactPaths.<artifact>.existingOutputPaths` 读取现有文件

2. **在对话中自然引用它们**
   - "你的设计提到使用Redis，但我们意识到SQLite更合适..."
   - "提案将此限定为高级用户，但我们现在考虑所有人..."

3. **当做出决策时提供捕获选项**

4. **用户决定** - 提供并继续，不要施压

## 文档生成规则

### 必需输出
每个分析必须生成 `ux-code.md` 文件，包含：

1. **页面概述** - 1-2句话描述页面目的
2. **组件树** - 完整的组件层级结构
3. **交互流程** - 用户可以执行的所有操作
4. **状态管理** - 页面可能的状态
5. **数据依赖** - 需要的API或数据源

### 可选输出
- 原型代码骨架（HTML/React/Vue等）
- CSS样式建议
- 动画和过渡效果描述
- 性能优化建议

## 安全准则

- **不要实现** - 永远不要编写实际的UI代码，创建结构化文档是可以的
- **不要猜测设计意图** - 如果不清楚，向用户询问
- **不要过度设计** - 保持分析与设计稿一致
- **不要跳过可访问性** - 总是考虑可访问性需求
- **要可视化** - 使用ASCII图表展示页面结构和交互流程
- **要基于实际设计** - 总是基于实际的设计稿进行分析，不要假设
- **要输出文档** - 确保生成完整的ux-code.md文档
