实现来自 msdd 变更的任务。

**存储选择：** 如果用户指定了存储（存储是在此机器上注册的独立 msdd 仓库）或工作在其中一个存储中，请运行 `msdd store list --json` 来发现已注册的存储 ID，然后在读取或写入规范和变更的命令（`new change`、`status`、`instructions`、`list`、`show`、`validate`、`archive`、`doctor`、`context`、`view`）上传递 `--store <id>`。其他命令不接受该标志。命令打印的提示已经包含该标志；在后续操作中保持它。如果没有存储，命令将作用于最近的本地 `msdd/` 根目录。

**输入**：可选指定变更名称。如果省略，检查是否可以从对话上下文中推断。如果模糊或不明确，你必须提示可用的变更。

**步骤**

1. **选择变更**

   如果提供了名称，则使用它。否则：
   - 如果用户提到了变更，从对话上下文中推断
   - 如果只有一个活跃变更存在，则自动选择
   - 如果不明确，运行 `msdd list --json` 获取可用的变更并让用户选择一个

   始终宣布："正在使用变更：<name>"以及如何覆盖（例如，`/opsx-apply <other>`）。

2. **检查状态以了解模式**
   ```bash
   msdd status --change "<name>" --json
   ```
   解析 JSON 以了解：
   - `schemaName`：正在使用的工作流（例如 "spec-driven"）
   - `planningHome`、`changeRoot` 和 `actionContext`：规划范围和编辑约束
   - 哪个产物包含任务（通常是 spec-driven 的 "tasks"，其他请检查状态）

3. **获取应用指令**

   ```bash
   msdd instructions apply --change "<name>" --json
   ```

   这返回：
   - `contextFiles`：产物 ID -> 具体文件路径数组（因模式而异 - 可能是 proposal/specs/design/tasks 或 spec/tests/implementation/docs）
   - 进度（总数、已完成、剩余）
   - 带状态的任务列表
   - 基于当前状态的动态指令
   - 可选的 `context`：从选定根目录获取的当前必需项目指令输入
   - 可选的 `operationGuidance`：当前应用的建议指导

   **处理状态：**
   - 如果 `state: "blocked"`（缺少产物）：显示消息，建议使用 msdd-continue-change（如果未安装，运行 `msdd status --change "<name>" --json` 查看下一个产物，以及 `msdd instructions <artifact-id> --change "<name>" --json` 了解如何创建它）
   - 如果 `state: "all_done"`：祝贺，建议归档
   - 否则：继续实现

   将 `context` 视为必需的提示级输入。阅读并考虑它，并在实现时应用相关的项目事实、约定和约束。
   将 `operationGuidance` 视为可选的附加建议。阅读并考虑每个条目，并遵循与内置工作流兼容且适用的条目。

   保持这两个字段与 CLI 返回的状态、缺失产物、任务、进度、`contextFiles` 和内置 `instruction` 分开。它们不是任务完成的证据，不替代内置指令，并且不允许绕过阻塞状态。如果上下文与内置指令、明确的用户选择或 CLI 控制的值冲突，请报告冲突并保留控制值。如果指导不适用或与这些控制输入冲突，请不遵循它并解释原因。这些是提示级行为契约，而非可执行检查。

4. **读取上下文文件**

   从应用指令输出中读取 `contextFiles` 下列出的每个文件路径。
   文件取决于使用的模式：
   - **spec-driven**：proposal、specs、design、tasks
   - 其他模式：遵循 CLI 输出中的 contextFiles

   不要将 `context` 或 `operationGuidance` 逐字复制到实现文件或规划产物中，除非用户单独要求该内容。

5. **显示当前进度**

   显示：
   - 正在使用的模式
   - 进度："N/M 个任务完成"
   - 剩余任务概述
   - 来自 CLI 的动态指令

6. **实现任务（循环直到完成或阻塞）**

   对于每个待处理任务：
   - 显示正在处理哪个任务
   - 进行所需的代码更改
   - 保持更改最小且集中
   - 在任务文件中标记任务完成：`- [ ]` → `- [x]`
   - 继续下一个任务

   **如果以下情况则暂停：**
   - 任务不明确 → 请求澄清
   - 实现揭示设计问题 → 建议更新产物
   - 遇到错误或阻塞 → 报告并等待指导
   - 用户中断

7. **在完成或暂停时，显示状态**

   显示：
   - 本次会话完成的任务
   - 整体进度："N/M 个任务完成"
   - 如果全部完成：建议归档
   - 如果暂停：解释原因并等待指导

**防护栏**
- 继续处理任务直到完成或阻塞
- 开始前始终读取上下文文件（从应用指令输出）
- 如果任务不明确，暂停并询问后再实现
- 如果实现揭示问题，暂停并建议更新产物
- 保持代码更改最小且针对每个任务
- 完成每个任务后立即更新任务复选框
- 遇到错误、阻塞或不清楚的需求时暂停 - 不要猜测
- 使用 CLI 输出中的 contextFiles，不要假设特定文件名
- 不要将上下文或操作指导用作任务完成的证明
- 应用相关的项目上下文；报告与控制工作流输入的冲突
- 考虑每个指导条目；解释任何不适用或冲突的建议
- 不要将运行时上下文或操作指导复制到实现文件或规划产物中
- 保留 CLI 控制的阻塞/就绪/全部完成行为和完成标准

**流动工作流集成**

此技能支持"对变更的操作"模型：

- **可以随时调用**：在所有产物完成之前（如果任务存在）、部分实现之后、与其他操作交错进行
- **允许产物更新**：如果实现揭示设计问题，建议更新产物 - 不锁定阶段，灵活工作
